    Rich-Mention Agent Delegation in Chat¶

    Status: Draft — design approved 2026-05-13. Companion docs: docs/architecture/rich_mentions.md (existing mention system), docs/architecture/llms/README.md (agent/tool architecture).

    Problem¶

    OpenContracts' chat surfaces (ChatTray for document chat, CorpusChat for corpus chat) bind one agent to a WebSocket connection at connect time — default-document-agent or default-corpus-agent. Users cannot invoke a different agent mid-conversation, can't see which agent is answering, and have no UX for switching context to a corpus-scoped specialist.

    Meanwhile, the rich-mention system (docs/architecture/rich_mentions.md) already supports @agent in the thread composer — but mentions are decorative. They render as chips, navigate to a detail page, and do nothing in chat.

    This design makes @-mentioning an agent in a chat message do work: the mentioned agent is delegated to as a sub-agent for that turn, while the default agent for the scope (the conductor) stays in charge of the conversation.

    Decisions (locked in)¶

    Decision Choice
    Semantic Mention-as-tool. Conductor remains in charge; mentioned agents become delegation tools the conductor can call.
    Toolset scope Per-turn allowlist: delegation tools exist only for agents @-mentioned in the current user message. Zero baseline delegation surface.
    Sub-agent context Conductor prompt + scope tools. Sub-agent sees only the prompt the conductor passes plus the doc/corpus tools attached to the connection. No conversation history.
    Sub-agent approvals Bubble up with attribution. Approvals raised inside a sub-agent reach the user via the existing ASYNC_APPROVAL_NEEDED flow, enriched with requesting_agent: { id, slug, name }.
    Attribution UX Timeline entry by default, pin=true promotes to a bubble. The conductor decides per-call via the delegation tool's pin argument.
    Composer scope Staged. Phase 1: lightweight agent-only @-picker overlay on the existing <textarea>. Phase 2 (out of scope here): replace the textarea with MessageComposer to bring all five mention types into chat.

    Assumptions¶

    1. Wire grammar. Agent mentions serialize as markdown links — [@<slug>](/agents/<slug>) for global agents, [@<slug>](/c/<corpus-slug>/agents/<slug>) for corpus-scoped. Same URL grammar rich_mentions.md already documents. The body of the WebSocket payload ({ query: <markdown> }) remains the single source of truth. No new @agent: text token.
    2. Scope matrix.
    3. Doc-without-corpus chat → global agents only.
    4. Doc-in-corpus chat → global agents + that corpus's agents.
    5. Corpus chat → global agents + that corpus's agents.
    6. Cross-corpus agents never visible.
    7. Anonymous users. Same visible_to_user gate as everything else — anonymous users see public/global agents only. Delegation works for them on those.
    8. Multiple @-mentions in one message. All of them become delegation tools for that turn; the conductor decides which (and how many) to call.
    9. Unresolvable mention (deleted, no permission, unknown slug, out of scope) → renders as a normal styled chip via the existing mentioned_resources graceful-degradation contract, and no delegation tool is attached. Silent fallback. Never an error frame.
    10. Picker source. Reuse useUnifiedMentionSearch scoped to type=agent, filtered by the active corpusId/documentId.
    11. GraphQL. Chat ChatMessageType grows a mentioned_resources resolver. Initial scope: agents only at read time, but the underlying extractor handles all five types so Phase 2 is a switch flip.

    Boundaries¶

    • Frontend composer stays a <textarea> in Phase 1 with an @-picker overlay that emits the rich-mention markdown grammar. No client-side mention parsing; the body is the contract.
    • WebSocket payload contract is unchanged: { query: <raw markdown> }. No agent IDs in the payload.
    • UnifiedAgentConsumer keeps its connection-bound agent_config (the conductor). On each user turn it (1) parses agent URLs from the body via a shared extractor, (2) filters via visible_to_user(user) + scope rules, (3) materializes one CoreTool per surviving agent, (4) augments the conductor's toolset for this turn only, (5) relays sub-agent streaming through the socket with new optional metadata.
    • Conductor's tool surface is per-turn, not per-connection. Augmentation is strictly additive; the conductor's normal tools still apply.
    • Delegation tool's scope tools mirror the current connection's bound scope (doc/corpus). Sub-agents get the same data-access boundary the conductor does — just no conversation history and only the conductor-supplied prompt.
    • Mention resolver (MentionedResourceType) extends to chat ChatMessage so persisted attribution renders identical chips on history reload.
    • Approval flow is unchanged structurally; ASYNC_APPROVAL_NEEDED payload grows an optional requesting_agent block.

    Sources of truth¶

    • Permission gate: AgentConfiguration.objects.visible_to_user(user). Called once per turn at parse time.
    • Scope gate: a small predicate on the consumer layered on top of visible_to_user. Silent rejection (no error frame).
    • Mention URL extractor: lives in opencontractserver/llms/agents/mention_extractor.py (new), shared between MessageType.mentioned_resources (existing), the new ChatMessageType.mentioned_resources, and the consumer's per-turn parser. DRY-compliant.

    Backend internals¶

    Shared mention extractor¶

    New module: opencontractserver/llms/agents/mention_extractor.py

    Pure parsing — no DB, no permissions, no I/O.

    @dataclass(frozen=True)
class ExtractedMention:
    type: Literal["agent", "user", "corpus", "document", "annotation"]
    slug: str | None            # agent slug, corpus/doc slug, user slug
    id: int | None              # annotation id when applicable
    corpus_slug: str | None     # for corpus-scoped agents: /c/{...}/agents/{slug}
    url: str                    # the raw URL as written (stable resolver-key match)
    label: str                  # the visible link text

    def extract_mentions(markdown: str) -> list[ExtractedMention]: ...
def extract_agent_mentions(markdown: str) -> list[ExtractedMention]: ...

    The existing MessageType.resolve_mentioned_resources switches over to call extract_mentions(...). No change to its return shape or permission gate.

    Delegation tool factory¶

    New module: opencontractserver/llms/tools/delegation_tools.py

    Per-turn flow inside UnifiedAgentConsumer.receive(...):

    mentions = extract_agent_mentions(user_query_markdown)
visible_agents = (
    AgentConfiguration.objects.visible_to_user(user)
    .filter(slug__in=[m.slug for m in mentions], is_active=True)
)
in_scope_agents = filter_by_scope(visible_agents, corpus_id, document_id)
delegation_tools = [
    build_delegation_tool(agent, stream_relay_factory, user, corpus, document, conversation)
    for agent in in_scope_agents
]
conductor_tools = base_tools + delegation_tools  # per-turn union

    Tool naming: delegate_to_<slug_as_snake_case>.

    Each tool:

    • Description = agent.description verbatim. This is what the LLM sees when picking. Encourages good agent descriptions.
    • Schema = { prompt: str (required), pin: bool = False }.
    • Body (async):
    • Build a fresh AgentConfig for the target agent (slug → AgentConfiguration → AgentConfig via the existing factory).
    • Attach scope tools matching the connection: document_id bound → doc read/search tools; corpus_id bound → corpus tools.
    • Spawn the sub-agent via pydantic_ai_factory.create_agent(...).
    • Stream the sub-agent's output through the StreamRelay. If pin=True, the relay emits a parallel ASYNC_START/CONTENT/FINISH sequence with a new message_id and persists a ChatMessage row at finish. If pin=False, the relay accumulates silently.
    • If the sub-agent triggers an approval, the relay emits ASYNC_APPROVAL_NEEDED enriched with requesting_agent and awaits resolution (re-using the consumer's existing approval-future machinery).
    • Return { "result": <final_text>, "pinned_message_id": <id_or_None> }. Conductor gets the string back; the metadata also records on the conductor's timeline entry so the frontend renders the chip on the timeline row.

    Fault tolerance follows the issue #820 pattern from core_tools: operational errors are caught and returned as error strings; PermissionError/ToolConfirmationRequired propagate.

    Per-turn instantiation (not cached): the conductor's normal tools are static at connect time, but delegation tools depend on what the user typed this turn. Building them per-turn avoids stale references. Cost is small — a list of CoreTool wrappers.

    Stream relay¶

    @dataclass
class StreamRelay:
    parent_message_id: str
    agent: AgentConfiguration
    pin: bool
    on_token: Callable[[str], Awaitable[None]]
    on_thought: Callable[[str, dict], Awaitable[None]]
    on_approval: Callable[[dict], Awaitable[ApprovalDecision]]
    on_finish: Callable[[str], Awaitable[Optional[int]]]  # returns persisted msg id when pinned

    The relay isolates the sub-agent from the WebSocket — it wires sub-agent events to the consumer's _send_safe(...), adding two metadata fields to every outbound frame:

    • agent_id: GraphQL global id of the sub-agent.
    • parent_message_id: the conductor's message_id.

    For pin=True, on_finish writes a new ChatMessage row before emitting ASYNC_FINISH, so the frontend can immediately key it. Timestamp is now() — it sorts between the conductor's start and finish on reload.

    For pin=False, the relay buffers tokens and emits an ASYNC_THOUGHT (type=tool_call) at start and an ASYNC_THOUGHT (type=tool_result) at finish, on the conductor's message_id — the existing timeline-entry pattern with agent_id added to the data payload.

    Streaming protocol deltas¶

    All additive. No frame renamed or removed.

    Frame Existing fields New optional fields
    ASYNC_START content, data.message_id data.agent_id, data.parent_message_id (pinned sub-agent only)
    ASYNC_CONTENT content, data.message_id data.agent_id, data.parent_message_id
    ASYNC_FINISH content, data.message_id, data.sources?, data.timeline?, data.context_status? data.agent_id, data.parent_message_id
    ASYNC_THOUGHT content, data.tool_name, data.args, data.tool_result, data.compaction data.agent_id when the thought represents a delegation call/result
    ASYNC_APPROVAL_NEEDED data.message_id, data.pending_tool_call data.requesting_agent: { id, slug, name }
    ASYNC_APPROVAL_RESULT data.message_id, data.decision data.requesting_agent (mirrored for symmetry)

    Frontend treats every new field as optional and falls back to existing behavior when absent. Backward and forward compatible.

    Consumer changes (concrete diff shape)¶

    config/websocket/consumers/unified_agent_conversation.py:

    1. receive(...) gains a pre-dispatch step: extract mentions, build delegation tools, augment conductor toolset.
    2. New helper _resolve_delegation_targets(self, mentions) -> list[AgentConfiguration] encapsulating visible_to_user + scope filter.
    3. New helper _build_stream_relay(parent_message_id, agent, pin) -> StreamRelay.
    4. The existing approval-pending future is keyed by (message_id, requesting_agent_id_or_none) instead of just message_id — the conductor's own approval uses None for the second tuple element, sub-agent approvals use the sub-agent's id. Prevents collisions when a conductor approval and a sub-agent approval coexist on the same turn.

    No changes to _resolve_agent_config (the connection-bound default), no changes to params parsing, no changes to permission validation. The delegation surface is strictly additive per turn.

    Scope filter¶

    def filter_by_scope(qs, corpus_id, document_id):
    # Global agents always pass
    # Corpus-scoped agents pass when corpus_id matches OR document is in that corpus
    if not corpus_id and not document_id:           # standalone doc chat
        return qs.filter(scope="GLOBAL")
    if corpus_id:
        return qs.filter(Q(scope="GLOBAL") | Q(corpus_id=corpus_id))
    # document_id without corpus_id: look up the doc's corpus
    doc_corpus_id = await Document.objects.values_list("corpus_id", flat=True).aget(pk=document_id)
    if doc_corpus_id:
        return qs.filter(Q(scope="GLOBAL") | Q(corpus_id=doc_corpus_id))
    return qs.filter(scope="GLOBAL")

    (Sync/async details handled per the codebase's existing patterns.)

    Persistence¶

    ChatMessage already carries the columns we need — agent_configuration FK and parent_message self-FK. No schema migration.

    Row shapes per scenario¶

    A — User turn, no mentions (today's flow, unchanged):

    ChatMessage[HUMAN]       content="hello"               agent_configuration=NULL
ChatMessage[ASSISTANT]   content="hi"                  agent_configuration=<conductor>
                                                       data={timeline: [...]}

    B — User turn, mentions @research-bot, conductor delegates unpinned:

    ChatMessage[HUMAN]       content="[@research-bot](/agents/research-bot) summarize §3"

ChatMessage[ASSISTANT]   content="Here's a summary..." agent_configuration=<conductor>
                                                       data={
                                                         timeline: [
                                                           {type: "tool_call",
                                                            tool: "delegate_to_research_bot",
                                                            agent_id: <research-bot id>,
                                                            agent_slug: "research-bot",
                                                            args: {prompt: "...", pin: false}},
                                                           {type: "tool_result",
                                                            tool: "delegate_to_research_bot",
                                                            agent_id: <research-bot id>,
                                                            result: "<sub-agent's full text>"}
                                                         ]
                                                       }

    Single row for the assistant. Sub-agent attribution lives entirely in the timeline JSON.

    C — User turn, mentions @research-bot, conductor delegates pinned:

    ChatMessage[HUMAN]       content="[@research-bot](/agents/research-bot) summarize §3"

ChatMessage[ASSISTANT]   content="<sub-agent's full text>"
                                                       agent_configuration=<research-bot>
                                                       parent_message=<conductor row>
                                                       data={
                                                         delegated_from: <conductor msg id>,
                                                         pinned: true,
                                                         sources: [...]
                                                       }

ChatMessage[ASSISTANT]   content="<conductor's synthesis>"
                                                       agent_configuration=<conductor>
                                                       data={
                                                         timeline: [
                                                           {type: "tool_call",  ...,  args: {pin: true}},
                                                           {type: "tool_result", ...,
                                                            pinned_message_id: <sub-agent row id>,
                                                            result: "<sub-agent's text>"}
                                                         ]
                                                       }

    Two assistant rows. Sub-agent row writes first (its id embeds in the conductor's timeline). parent_message on the sub-agent row points to the conductor row — set in a small post-write step once the conductor row exists. created_at ordering keeps them adjacent on reload.

    Reload-time ordering¶

    Frontend already sorts combinedMessages by timestamp. Sub-agent row's created_at is between the conductor's ASYNC_START and ASYNC_FINISH times, so it sorts visually between them — matching the in-flight rendering order. No new sort logic.

    Multiple pinned delegations in one conductor turn sort by their own created_at in invocation order.

    Persistence write points (all inside the consumer)¶

    Event Write
    User frame received Persist ChatMessage[HUMAN] (existing)
    Conductor ASYNC_START Create ChatMessage[ASSISTANT] row with state="in_progress" (existing)
    Pinned sub-agent ASYNC_START (via relay) Create ChatMessage[ASSISTANT] row, agent_configuration=<sub-agent>, state="in_progress" (NEW)
    Pinned sub-agent ASYNC_FINISH Update sub-agent row: content, state="complete", data.sources (NEW)
    Conductor's delegation tool returns Append tool_result entry to conductor's data.timeline (existing pattern, enriched)
    Conductor ASYNC_FINISH Update conductor row: content, state="complete". Then point each pinned sub-agent row's parent_message at the conductor row (NEW small back-link step).

    parent_message linkage is a nice-to-have for ancestry traversal in future queries. Not load-bearing for rendering — the frontend renders purely from timestamp + agent_configuration.

    GraphQL¶

    ChatMessageType.mentioned_resources¶

    Mirror the thread MessageType.resolve_mentioned_resources pattern (currently in conversation_types.py around line 65/123). The chat type lives at conversation_types.py:314.

    class ChatMessageType(AnnotatePermissionsForReadMixin, DjangoObjectType):
    mentioned_resources = graphene.List(MentionedResourceType)

    class Meta:
        model = ChatMessage
        ...

    def resolve_mentioned_resources(self, info):
        mentions = extract_mentions(self.content)
        return resolve_mentions_for_user(mentions, info.context.user)

    resolve_mentions_for_user(...) is factored out of the existing MessageType.resolve_mentioned_resources body (same permission gate, same return shape). Two callers, one implementation.

    Surfacing the pinned sub-agent on a ChatMessage¶

    The frontend needs to know which agent wrote each pinned sub-agent row. The agent_configuration FK gives us that natively. Expose it minimally:

    type ChatMessageType {
  ...existing fields
  agentConfiguration: AgentConfigurationType
  mentionedResources: [MentionedResourceType]
}

    AgentConfigurationType likely already exists for the picker; if not, add a shallow projection (id, slug, name, description, scope, corpus) — not a DjangoObjectType exposing the full agent. Same philosophy as MentionedResourceType: a projection, not a back door.

    GET_CHAT_MESSAGES in frontend/src/graphql/queries.ts grows a small fragment to fetch agentConfiguration { id slug name } and mentionedResources { ... }.

    Explicitly NOT changing¶

    • No new tables.
    • No new Django model fields.
    • No changes to AgentConfiguration or its visibility manager.
    • No changes to Conversation model.
    • No changes to existing GraphQL types' shape — only additions of optional fields.

    The only schema delta in this entire feature is the consumer's outbound frame metadata, which is additive.

    Frontend¶

    Phase-1 composer overlay¶

    Keep ChatTray/CorpusChat's <textarea>. Add an agent-only @-suggest overlay that:

    1. Watches newMessage for the @ trigger. On a typed @ + fragment, opens a popover anchored to the textarea caret.
    2. Queries via the existing useUnifiedMentionSearch, scoped to type=agent and parameterized with corpusId/documentId so the hook applies the same scope filter the backend will.
    3. Re-uses UnifiedMentionPicker in agent-only mode (types={["agent"]} prop, or a slim wrapper). Re-use, don't fork.
    4. On selection, replaces the in-progress @frag with the markdown-link form:
    5. Global: [@<slug>](/agents/<slug>)
    6. Corpus-scoped: [@<slug>](/c/<corpus-slug>/agents/<slug>) Calls a helper buildAgentMentionLink mirroring the rich-mention grammar.
    7. Closes on Escape, on selection, on caret leaving the trigger context, or on Space without a selection.

    No TipTap. No node types. The textarea remains a plain markdown string — same { query } payload over the wire.

    New files (frontend): - frontend/src/components/chat/AgentMentionPopover.tsx — popover UI + selection state. - frontend/src/hooks/useAgentMentionTrigger.ts — caret-watcher + textarea integration (returns { isOpen, fragment, caretPos, onSelect, onDismiss }).

    Modified files (frontend): - ChatTray.tsx: wire useAgentMentionTrigger into the existing textarea; render <AgentMentionPopover> near the input. The hook patches value on selection and refocuses. - CorpusChat.tsx: same pattern. - MarkdownMessageRenderer.tsx: already handles agent mention chips per rich_mentions.md — needs to be invoked on ChatMessage bodies. The chat-message widget switches from plain markdown rendering to the same MarkdownMessageRenderer the threads use. Major DRY win even in Phase 1.

    Phase-2 migration to MessageComposer becomes "swap the textarea for the rich composer, delete AgentMentionPopover and useAgentMentionTrigger." Clean uninstall.

    Attribution rendering¶

    Four surfaces:

    A. Mention chip in the user's own message. Already solved by rich_mentions.md's renderer. Free once MarkdownMessageRenderer is wired into chat.

    B. Pinned sub-agent bubble. The existing ChatMessage widget gets a small enhancement: when agentConfiguration is present and not the conversation's conductor, render an agent chip in the bubble header (small avatar + name, same visual language as the mention chip) plus a subtle left-edge accent in the agent's scope color (global vs corpus) so the visual rhythm of conductor-bubble / sub-agent-bubble / conductor-bubble is scannable.

    C. Timeline entry attribution. The existing TimelineEntry UI already renders tool_call/tool_result rows. Add a variant: when data.agent_id is present, the row shows the agent chip instead of the bare tool name (since delegate_to_research_bot reads worse than @research-bot). Full tool name available on hover/expand for power users.

    D. Approval modal attribution. ApprovalOverlay.tsx's modal grows an optional header: when pendingApproval.requestingAgent is present, show <chip>@research-bot</chip> is asking to: <tool name> instead of the bare Tool: <name>. Backwards-compatible default when the field is absent.

    Streaming integration¶

    The existing handleAgentMessage switch covers ASYNC_START/CONTENT/FINISH/THOUGHT/APPROVAL_NEEDED. No new cases. The new metadata fields are read off data.* inside the existing cases:

    • ASYNC_START with data.agent_id + data.parent_message_id → call appendStreamingTokenToChat with the sub-agent's message_id; the new message gets agentConfiguration set on ChatMessageProps so the chip renders immediately.
    • ASYNC_THOUGHT with data.agent_id → existing appendThoughtToMessage flow; the timeline entry carries the new field through to the renderer.
    • ASYNC_APPROVAL_NEEDED with data.requesting_agent → existing setPendingApproval flow; the modal renders the new chip.

    Net change in ChatTray/CorpusChat: ~20 LOC each. The streaming layer is mostly future-proofed already; new fields ride along as opaque pass-throughs.

    Error handling and graceful degradation¶

    • Mention to invisible/deleted agent → renders as a chip via the existing mentioned_resources graceful-degradation contract; no delegation tool attached. Silent.
    • Mention to out-of-scope agent (corpus-scoped agent mentioned from a different scope) → same: chip without behavior, no error frame. Silent.
    • Sub-agent raises an operational exception → caught inside the delegation tool body, returned as an error string the conductor can read (and decide how to handle).
    • Sub-agent raises PermissionError / ToolConfirmationRequired → propagates through the delegation tool to the consumer's outer handler, same as the conductor's own tools.
    • Sub-agent approval rejected → sub-agent receives a rejected decision, returns a tool-error result to the conductor. Conductor decides how to respond.
    • Multiple @-mentions of the same agent in one message → deduplicated by the extractor; one delegation tool per agent.
    • Mention resolution race (agent visible at parse time, deleted before delegation runs) → delegation tool body re-checks visibility on entry; if gone, returns an error string. Single source of truth remains visible_to_user.

    Out of scope (Phase 2 and beyond)¶

    • Replacing <textarea> with MessageComposer (Phase 2).
    • User-initiated post-hoc pin promotion ("the user clicks a timeline entry to promote it to a bubble").
    • Multi-hop delegation. A sub-agent itself delegating to another sub-agent. Backend will reject (sub-agents get scope tools, not delegation tools).
    • @user / @corpus / @document / @annotation mentions behaving differently in chat. They will render as chips for free once Phase 2 unifies, but won't trigger any new behavior.
    • Per-agent custom approval UX (each sub-agent still uses the global ApprovalOverlay).
    • Conversation-level pinned-delegate analytics (counts, etc.).
