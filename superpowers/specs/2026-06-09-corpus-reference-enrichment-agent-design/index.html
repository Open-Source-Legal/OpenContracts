    Corpus Reference Enrichment Agent — Design¶

    Date: 2026-06-09 Branch: feature/corpus-reference-enrichment (local, off origin/main) Status: Approved design; pre-implementation-plan

    1. Problem & Goal¶

    OpenContracts corpora (e.g. an SEC Form S-1 filing with its exhibits) are full of explicit references that today are invisible to the system as connections:

    • A primary S-1 cites its own exhibits ("Exhibit 10.1", the Certificate of Incorporation, the 2021 Credit Agreement).
    • Sections cite other sections ("See \"Risk Factors\"", "as described under Use of Proceeds").
    • Documents cite external law ("Section 145 of the Delaware General Corporation Law", "Section 4(a)(2) of the Securities Act").
    • Defined terms ("the Company", "Sponsor") are used across sections/documents.

    Goal: an agentic enrichment workflow, triggerable as a tool in chat (like the CAML writer), that crawls a corpus, inventories these references, annotates them, and creates the connecting relationships — reusing existing OpenContracts infrastructure wherever possible. References to external law must be normalized into a stub that can be tracked and joined cross-corpus later (cross-corpus linking is not supported today, but the data shape must anticipate it). The agent is v1; the same engine must be reusable in other ways later (e.g. a batch CorpusAction).

    This must be proven on a real S-1 corpus — specifically the loaded corpus id=19 ("Fervo Energy … Form S-1", which actually bundles Cerebras + Fervo S-1 primary documents and ~130 exhibits).

    2. Grounding facts (verified against the codebase and corpus 19)¶

    These findings shaped every decision below. They are load-bearing.

    2.1 Data-model constraints (verified in opencontractserver/annotations/models.py)¶

    • A Relationship cannot span two documents. A DB CheckConstraint (relationship_has_single_parent) and clean() force exactly one parent: either a document OR a structural_set, never both/neither. Permissioning (RelationshipManager.user_can) assumes its annotations resolve to that one document. → Within-document section→section links map onto Relationship; cross-document and cross-corpus links do not.
    • Annotation.link_url is a validated field (validate_link_url): only http(s):// absolute URLs and site-relative paths beginning with / are allowed (javascript:/data: rejected). The frontend (frontend/src/components/annotator/utils/urlAnnotation.ts) renders these clickable; site-relative paths route in-app via the SPA router (navigate()), external URLs open in a new tab with noopener,noreferrer. → A site-relative link_url like /corpus/19/document/146 is a ready-made, safe, in-app cross-document link mechanism.
    • Annotation.data is a JSONField "structured metadata sidecar" (first consumer: geocoding stamps {canonical_name, lat, lng, …} on OC_COUNTRY/OC_STATE/OC_CITY). Untyped, application-owned shape. → The sanctioned home for a normalized law payload {authority, section, canonical_key}.
    • Analysis can be created programmatically with an in-process (task_name-based, not remote-gremlin) Analyzer. Both Annotation and Relationship carry analysis (provenance/visibility) and created_by_analysis (privacy). → Provenance container for an enrichment run, enabling grouping, re-run, and cleanup.
    • Programmatic creation pattern (from opencontractserver/llms/tools/core_tools/annotations.py and document_indexing.py): corpus.ensure_label_and_labelset(...) → build unsaved Annotation(...) → set data/long_description → .save(); hierarchy via a second pass setting parent_id. Span format {"start": int, "end": int} for text docs; token JSON for PDFs.

    2.2 Corpus-19 reality (verified by querying the dev DB and reading text)¶

    • 130 documents: a ~900 KB primary S-1 plus exhibits (Ex 3.1 Certificate of Incorporation, 3.2 bylaws, 10.x material contracts, 21.1, 23.1, …).
    • Reference patterns confirmed present in the real text:
    • Law: 9× "… Delaware General Corporation Law" (incl. "Section 145 of …", "Section 203 of …"); "Section 4(a)(2) of the Securities Act", "Section 7(a)(2)(B) …", "Section 8(a) …".
    • Internal section refs: 49× See "…" / See the section … (incl. See "Risk Factors").
    • Doc↔Doc: exhibit references + an exhibit index.
    • Existing structure to reuse, not reinvent: label breakdown shows EXHIBIT_REFERENCE (15), Exhibit doc-type (126), SEC_HEADER (130), S-1 (130), OC_SECTION (20).
    • EXHIBIT_REFERENCE spans already mark "Exhibit 1.1" etc. but carry no link_url and no data — detection is partly done, resolution/linking is the gap this agent fills.
    • Zero annotations corpus-wide have link_url set — cross-doc linking is greenfield here.
    • OC_SECTION is sparse: 5/130 docs, 20 annotations, mostly-null parent. → The resolver must NOT assume a dense section index; it needs a heading-text fallback (and may optionally invoke the existing create_document_index tool to build an index when absent).

    2.3 Reusable agent infrastructure (verified)¶

    • CoreTool → PydanticAIToolWrapper with requires_corpus, requires_write_permission, requires_approval, parameter injection (document_id/corpus_id/user_id hidden from the LLM), per-call permission checks, and tool-output truncation. Register in tool_registry.py (AVAILABLE_TOOLS + FUNCTION_MAP).
    • PydanticAICorpusAgent (corpus-scoped) attaches corpus tools; the WebSocket consumer (config/websocket/consumers/unified_agent_conversation.py) already streams any tool's calls/approvals — no consumer changes needed.
    • The CAML writer (core_tools/caml_article.py) is the blueprint: read → propose → apply (requires_approval=True), writing back via ORM inside transaction.atomic().

    3. Architecture¶

    Deterministic engine, agent as orchestrator (chosen "Approach A" over LLM-driven crawl and pure-embedding-graph alternatives — see §9).

    Agent chat (corpus-scoped PydanticAICorpusAgent)
  │  scan_corpus_references(...)                    read-only  → inventory, no writes
  │  apply_corpus_reference_enrichment(...)         approval-gated write
  ▼
Services  (new package: opencontractserver/enrichment/)   pure, testable, service-layer compliant
  ReferenceExtractor   document text → typed candidate spans (grammars/regex)
  ReferenceResolver    candidate → concrete target (OC_SECTION index, doc titles, similarity_search)
  EnrichmentWriter     persist all rows in ONE transaction under an Analysis
  ▼
Persistence  (reuse existing + ONE new model)
  Annotation        mention span; label by type; normalized `data`; link_url when internal target
  Relationship      WITHIN-document section→section & definition→usage (renders today)
  CorpusReference   NEW first-class stub: cross-doc / cross-corpus / external-law
  Analysis          provenance container for the whole run (re-run / cleanup / visibility)

    Division of labor (DRY, no overlap): - Within-document links → existing Relationship (already rendered in the viewer). - Cross-boundary + external-law links → new CorpusReference. - Every reference (all types) → a mention Annotation so there is always a visible, clickable anchor in the document.

    4. New model: CorpusReference¶

    Lives in the annotations app (alongside Annotation/Relationship) to avoid new-app registration churn. Extends BaseOCModel (standard guardian permissioning, creator, is_public, timestamps).

    Field Type Purpose
    corpus FK Corpus source corpus
    reference_type char choices: LAW / DOCUMENT / SECTION / DEFINED_TERM discriminator
    source_annotation FK Annotation (CASCADE) the mention span (always set)
    target_annotation FK Annotation, null=True resolved internal target
    target_document FK Document, null=True resolved target document
    target_corpus FK Corpus, null=True future cross-corpus target
    canonical_key CharField(255), db_index, null=True cross-corpus join key: dgcl:145, securities-act:4(a)(2), term:change-of-control
    normalized_data JSONField, null=True {authority, section, …} / candidate list when unresolved
    confidence FloatField, default 1.0 resolver confidence
    resolution_status char choices: RESOLVED / UNRESOLVED / EXTERNAL EXTERNAL for law; UNRESOLVED when ambiguous
    created_by_analysis FK Analysis, null=True provenance/run grouping

    Constraints/indexes: - index on (corpus, reference_type) and on canonical_key (cross-corpus joins). - A natural-key uniqueness guard for idempotency — see §7.

    GraphQL: a read-only CorpusReferenceType + a corpus-scoped resolver (through a CorpusReferenceService). No mutations in v1 (creation is via the enrichment tool). A full frontend panel is out of scope for v1 (§8).

    5. Reference types → detect / normalize / store¶

    Type Detect (extractor) Normalize Store
    Law grammar: Section <N> of the <DGCL\|Delaware General Corporation Law\|Securities Act\|Securities Exchange Act\|Internal Revenue Code> (+ common variants) canonical_key (dgcl:145, securities-act:4(a)(2), exchange-act:…, irc:409a); normalized_data={authority,section} mention Annotation (label OC_REF_LAW, data=normalized) + CorpusReference(LAW, EXTERNAL)
    Doc↔Doc reuse/extend existing EXHIBIT_REFERENCE spans + exhibit cues ("Exhibit 10.1", "our Certificate of Incorporation") match exhibit number / title → target document in corpus set mention link_url=/corpus/<cid>/document/<did> + CorpusReference(DOCUMENT, RESOLVED)
    Internal section See "<Heading>", See the section …, under "<Heading>" resolve heading → OC_SECTION annotation (or heading-text fallback in same doc) within-doc Relationship + mention link_url to the section anchor
    Defined term (opt-in, capped) definition: "<Term>" means … / shall mean; usages: subsequent capitalized occurrences term:<slug> within-doc definition→usage Relationship; cross-doc usage → CorpusReference(DEFINED_TERM)

    Notes: - Mentions are non-structural (structural=False) so they're editable/ deletable by users with corpus write. - Where an EXHIBIT_REFERENCE span already exists for a detected doc reference, extend it (set link_url, create the CorpusReference) rather than creating a duplicate mention. - Section resolution degrades gracefully when OC_SECTION is absent: fall back to locating the heading text within the document and anchoring the link to that offset; optionally trigger create_document_index first.

    6. Agent surface (CAML-style read → approval-gated apply)¶

    Two new CoreTools, registered in tool_registry.py, attached to the corpus-scoped agent:

    • scan_corpus_references(corpus_id, types=[...], sample_n=...)
    • requires_corpus=True, read-only.

    • Runs ReferenceExtractor + ReferenceResolver across the corpus; returns an inventory: counts by type, sample resolved candidates, and the unresolved/ambiguous ones. No writes. Lets the user/LLM review before committing (mirrors read_corpus_caml_article / propose_caml_citation_match).

    • apply_corpus_reference_enrichment(corpus_id, types=[...])

    • requires_corpus=True, requires_write_permission=True, requires_approval=True.
    • Creates the Analysis (in-process analyzer), then all mention annotations, Relationships, and CorpusReferences in one transaction. Returns created counts + ids (mirrors apply_caml_article_edit).

    The WebSocket consumer already streams tool calls and the single approval gate — no consumer changes. The same EnrichmentWriter is later wrappable as a CorpusAction for batch/scheduled runs (the "eventually other ways" path) with no redesign.

    7. Data flow, error handling, idempotency¶

    • Flow: chat → scan (inventory, no writes) → user approves → apply (transactional writes under an Analysis) → results visible (OC_URL links clickable; Relationships render; CorpusReferences queryable via GraphQL).
    • Fault tolerance (issue #820): operational errors are caught and returned as strings to the LLM; security errors (PermissionError, ToolConfirmationRequired) propagate. Per-document failures are isolated (skip + log) and never abort the whole run.
    • Idempotent re-run: dedupe by natural key (document_id, span_hash, label, canonical_key); re-running enriches only new references and creates zero duplicates. A DB unique guard on the equivalent CorpusReference tuple backs this.
    • Ambiguous targets: when >1 candidate target exceeds threshold, store resolution_status=UNRESOLVED with the candidate list in normalized_data and no link_url — surfaced in the scan summary for human disambiguation (future: per-item approve, like CAML propose).
    • Visibility: mentions inherit corpus visibility; set the analysis FK for provenance/cleanup but not created_by_analysis (which would hide them from corpus readers).
    • Service-layer compliance: extractor/resolver/writer are services; tools and services reach models through the enrichment/annotations service layer — no inline Tier-0 (visible_to_user/user_can) fusions. CorpusReference access goes through a CorpusReferenceService.

    8. Scope & sequencing¶

    In scope (v1): 1. CorpusReference model + migration + CorpusReferenceService + read-only GraphQL type/resolver. 2. ReferenceExtractor (law + internal-section + doc/exhibit) with table-driven unit tests. 3. ReferenceResolver + EnrichmentWriter with integration tests (permissioning + idempotency). 4. scan_corpus_references + apply_corpus_reference_enrichment tools + registration. 5. Proof on corpus 19 (§10).

    Behind a flag / capped (v1): defined-term extraction (precision risk; default off or capped count).

    Out of scope (v1): - Full frontend panel for browsing CorpusReferences (read-only GraphQL only — enough to query/verify). OC_URL links + Relationships already render, so the proof is visible without new frontend. - Actual cross-corpus linking (the model anticipates it via target_corpus + canonical_key; wiring is a later initiative). - CorpusAction/batch wrapper (design leaves the seam; not built in v1). - Pure-embedding latent-similarity links (only explicit references in v1).

    9. Alternatives considered¶

    • B — LLM-driven crawl (agent reads every section, LLM extracts/resolves via tools): flexible and catches fuzzy semantics, but at 130 docs it is expensive, non-deterministic, hard to prove, and risks hallucinated targets. Rejected as the core; the LLM is retained as orchestrator/validator only.
    • C — pure embedding-similarity graph: links sections by cosine similarity. Finds latent themes but misses the explicit references that are the actual ask and cannot normalize citations. Rejected for v1 (possible later layer).
    • Substrate — reuse-only (no new model): fastest, zero schema risk, but the cross-corpus "connection" is only a query convention over annotation.data, never a first-class record. Rejected in favor of the layered approach (reuse + small CorpusReference model) per the stated cross-corpus future.
    • Substrate — new model as the sole store (annotations only mark spans): cleanest graph but more upfront work and duplicates what Relationship already does within-document. Rejected; we let Relationship keep its job.

    10. Testing & proof¶

    • Unit — ReferenceExtractor: table-driven grammar tests, e.g. "Section 145 of the Delaware General Corporation Law" → LAW/dgcl:145; "Section 4(a)(2) of the Securities Act" → securities-act:4(a)(2); Exhibit 10.1 → DOCUMENT candidate; See "Risk Factors" → SECTION candidate.
    • Unit — ReferenceResolver: exhibit-number→document-title match; heading→OC_SECTION (and heading-text fallback when index absent); canonical-key normalization.
    • Integration — EnrichmentWriter: creates correct annotations/ relationships/CorpusReferences with correct permissioning; idempotent re-run creates zero duplicates.
    • Tool-level: scan returns an inventory and writes nothing; apply is approval-gated and transactional.
    • Proof script (docs/test_scripts/corpus_reference_enrichment.md): run scan then apply on corpus 19; assert
    • N OC_REF_LAW mentions with canonical_key including dgcl:145, dgcl:203, securities-act:4(a)(2);
    • M internal-section Relationships;
    • K doc mentions with site-relative link_url; then verify in the viewer (links clickable & route in-app; relationships render) and via GraphQL (CorpusReference rows queryable by canonical_key).

    11. Constraints from project rules¶

    • No commits/pushes for this work session — local branch only (feature/corpus-reference-enrichment).
    • Pre-commit (black/isort/flake8) + yarn lint discipline before any eventual commit; E001 service-layer check must stay green.
    • No magic numbers (use constants files); no dead code (extend/replace existing EXHIBIT_REFERENCE handling rather than duplicating).
    • Changelog: add a changelog.d/<slug>.added.md fragment (not a direct CHANGELOG.md edit) when the work lands.
