- **Importing into a folder no longer replaces a same-named document in a different folder** (issue #2520, reported in #2515). `Corpus.import_content` (`corpuses/models.py`) ignored `folder` when generating a default path, so every file landed at `/documents/<filename>`, and `import_document` then treated the second file as a new version of the first: the first document disappeared from its folder and two unrelated files shared a version tree. The single-document upload service (`document_imports/services.py::import_document_for_user`) hit this directly, and the agent tool (`llms/tools/core_tools/text_document_import.py`) hit it through its own title-derived path. Both now use `CorpusPathService.resolve_folder_import_path` (`corpuses/services/paths.py`), which generates `/<folder path>/<filename>`, falling back to the default path if that exceeds `DocumentPath.path`'s length limit. A name match in the same folder versions that document, whether it sits at the folder path or at a legacy `/documents/<filename>` path, so no data migration is needed. Impact:
  - New foldered imports get folder-derived paths, which folder renames also keep in sync.
  - A name match only versions a document the importer can READ. Corpus write access alone no longer lets a foldered import supersede another user's private document; the import gets a disambiguated path instead.
  - `create_or_update_text_document` with no `folder_id` still updates by title, using the new `CorpusPathService.resolve_named_update_path`: it finds the document wherever it lives, and raises `ValueError` asking for `folder_id` if the title matches several folders.
  - `import_content` with no folder keeps its `/documents/<filename>` default.
  - An import that had to be disambiguated isn't matched by later imports of the same name, which add a document rather than a version. Nothing is hidden, but duplicates are possible in that case.
  - Documents already affected are not repaired automatically; their earlier version is still in the version history.
