# CROSS TXT/SPAN Enrichment Engineering Handoff

Date: 2026-07-15

## Scope and conclusion

This report covers the PR 2153 customs-ruling enrichment path when fed the
official CROSS bulk export. It is not a finding that the PDF pipeline is
broken. Real legacy `.doc` inputs successfully converted to PDF and produced
token annotations, HTS annotations, citation references, and graph edges in a
separate 100-document production-path run.

The official CROSS bulk exporter instead emits `text/plain` documents. Those
documents are parsed correctly and deliberately use character-span anchors
(`SPAN_LABEL`). The customs service currently rejects that valid representation
before it runs either regex. This is the direct cause of the zero-output 10K
run.

Do not solve this by converting the official TXT export to PDF. That would add
conversion, parser, storage, and CPU cost solely to satisfy an unnecessary
service precondition. OpenContracts already has a supported span-annotation
model and the generic enrichment writer already persists citation mentions as
spans when no PDF token layer exists.

## Reproduction and observed result

Test corpus: `PR2153 CROSS 10K - 2026-07-14 0845` (PK 96)

Input was generated by CROSS's official bulk exporter with `--limit 10000` and
`--batch-size 400`, then submitted through the production
`POST /api/imports/zip-to-corpus/` path. The imported corpus contains 10,000
active CROSS TXT documents plus the README. The CROSS documents have text
extracts and valid remapped producer sidecars; the issue is not missing source
text or failed parsing.

Running:

```bash
python manage.py enrich_customs_rulings --corpus-id 96 --owner admin
```

over all 10,000 documents took **4m57.89s** and returned:

| New output from this enrichment run | Result |
| --- | ---: |
| Documents scanned | 10,000 |
| Documents skipped | 10,000 |
| HTS annotations | 0 |
| Citation mentions | 0 |
| Corpus references | 0 |
| Resolved references | 0 |
| Document relationships | 0 |

This is deterministic, not an intermittent worker or GUI issue. The same code
path succeeds for PDF/TOKEN input: the 100 real CROSS `.doc` to PDF run created
298 HTS annotations, 390 citation mentions, 312 resolved references, and 312
document-relationship edges.

The zeroes above are the new rows created by this service, not a claim that the
corpus has no producer annotations at all. A corpus snapshot found 114 remapped
source `HTS_CODE` spans and one `CITED_RULING` span. Their representation has a
separate label-type/provenance problem described below; neither can substitute
for the missing enrichment references and graph.

## Root cause chain

### 1. The service rejects the supported TXT representation before detection

`load_document_text_and_layer()` intentionally returns:

```python
return doc_text, None, SPAN_LABEL
```

for `text/plain` (and DOCX) documents. See
`opencontractserver/utils/span_projection.py:24-69`.

The customs service then rejects every such result:

```python
if ann_type != TOKEN_LABEL or layer is None:
    summary.documents_skipped_not_pdf += 1
    continue
```

See `opencontractserver/enrichment/services/customs_ruling_citation_service.py:220-235`.
The `continue` happens before `_write_hts_annotations()` or
`_build_citation_resolutions()` is called. Therefore no regex, resolution, or
writer defect can explain the immediate zero-output run; they are never reached.

The method's comment says a PDF page and bounding box are required to be
"useful." That is a product decision accidentally encoded as a format gate.
OpenContracts has a functional text renderer and stores correct character
offsets for text documents, so a span annotation is useful and clickable even
without PDF geometry.

### 2. HTS persistence is token-only even after the first gate is removed

Removing the skip by itself will make detection execute, but HTS creation will
still fail to represent TXT results correctly. `_write_hts_annotations()`:

- requests an `HTS_CODE` label with `label_type=TOKEN_LABEL`;
- always calls `project_span_to_token_annotation(layer, ...)`; and
- always writes `annotation_type=TOKEN_LABEL`.

See `customs_ruling_citation_service.py:308-373`. A text document has no
`layer`, so the current projection call cannot produce an annotation. The
implementation needs an explicit span branch, not a `try/except` that silently
skips TXT matches.

### 3. Citation persistence has the right fallback, but the service never lets
it run and its text-page sentinel is wrong

`EnrichmentWriter._get_or_create_mention()` already creates a `SPAN_LABEL`
annotation when PDF projection is unavailable:

```python
json_payload = {"start": cand.start, "end": cand.end}
ann_type = SPAN_LABEL
page = 1
```

See `opencontractserver/enrichment/writer.py:222-321`. It also deduplicates
both token and span representations and can later upgrade an old span mention
to a token mention if a PDF representation becomes available.

`page = 1` is itself a TXT UX defect. The canonical text-anchor path uses
`page = 0` as the no-page sentinel and the frontend suppresses that value. See
`opencontractserver/utils/annotation_anchoring.py:155-185`. A writer-generated
text citation currently advertises a nonexistent page, which can render as a
misleading page number in the UI. Change the generic writer's span fallback to
use `page = 0`; use the canonical text-span JSON shape with `start`, `end`, and
`text` where the renderer/anchorer expects it.

`_build_citation_resolutions()` receives `layer` but does not use it. See
`customs_ruling_citation_service.py:375-417`. Once TXT documents are allowed
through, it can create normal `Candidate` and `Resolution` objects and delegate
the mention to `EnrichmentWriter`; no new citation persistence subsystem is
needed.

### 4. Existing TXT sidecars have label-type and reference-label debt

The official exporter ships producer labels as `TOKEN_LABEL` because that is
what the import contract accepts, but the text anchorer correctly writes the
resulting annotation as `SPAN_LABEL`. The integration test documents this
intentional mismatch at
`opencontractserver/tests/test_zip_import_integration.py:2594-2605`, while the
anchorer emits the actual span at
`opencontractserver/utils/annotation_anchoring.py:155-185`.

That means the existing `HTS_CODE` producer rows in this corpus are
`Annotation.annotation_type=SPAN_LABEL` attached to an
`AnnotationLabel.label_type=TOKEN_LABEL`. Do not replicate this mismatch in new
enrichment output. `ensure_label_and_labelset()` keys labels by `(text,
label_type)`, so a correctly typed `HTS_CODE` span label is a distinct label row
and a naive implementation would create duplicate highlights. The current HTS
dedupe is also insufficient: it filters only the token label and only
`data.char_span.start`, while imported spans use `json.start`.

The source `CITED_RULING` label cannot become a `CorpusReference` source by
itself. `CorpusReference.save()` requires a document reference mention to carry
the canonical `OC_REF_DOC` label
(`opencontractserver/annotations/models.py:2030-2054`). The enrichment writer
will create that correctly typed reference mention, but it will be visually
parallel to the producer's `CITED_RULING` span unless the data is reconciled.

Make the policy explicit before coding:

1. For HTS, either normalize/relabel matching legacy producer spans to a proper
   `HTS_CODE` span label, preserving source provenance in `data`, or retain them
   as source evidence and suppress duplicate enrichment highlights while a
   deliberate migration/backfill corrects their label type.
2. For citations, the safe MVP is a dedicated `OC_REF_DOC` span mention plus
   its `CorpusReference`, while retaining the source `CITED_RULING` annotation.
   A follow-up reconciliation/migration can merge or relabel source spans if
   product wants one visual highlight. Do not attach a reference to
   `CITED_RULING` and bypass the model invariant.

### 5. Canonical ruling identity is independently broken for the official
export

This is not why the 10K run has zero annotations: the TXT gate fires first. It
will, however, prevent most citation resolution after span support is added.

The service indexes a target document by a normalized `Document.title`:

```python
title_index = {
    _ruling_number_from_title(doc.title): doc
    for doc in documents if doc.title
}
```

See `customs_ruling_citation_service.py:201-208`. The helper only strips an
extension and uppercases the entire title.

The dict comprehension also silently overwrites an earlier document when two
documents normalize to the same identifier. Canonical-index construction must
detect and report ambiguity rather than choose the last row by iteration order.

The official exporter puts the human-readable ruling subject in `meta.csv`
`title`, not the ruling number:

```python
title = r.subject or f"{r.collection} {r.ruling_number}"
```

See `CROSS-Corpus/src/crossfeed/export/oc_bulk.py:235-246`. A detected `H022844`
therefore cannot match the target's subject title. Titles are also not unique in
the tested 10K corpus: there are 9,682 unique title strings, 217 normalized
collision groups spanning 594 documents, and 332 titles containing C0 control
characters. They are display metadata, not a reliable identifier.

The source path is the immediately usable canonical identity for this exporter:
`/HQ/H022844.txt` has `H022844` as its basename stem. `DocumentPath` is the
source of truth for current corpus membership and paths
(`opencontractserver/documents/models.py:812-915`), and the import code already
uses path maps to resolve cross-batch relationships
(`opencontractserver/tasks/import_tasks.py:595-632`).

Do not assume a new `ruling_number` column in `meta.csv` will magically become
`Document.custom_meta`: the current metadata parser only understands
`source_path`, `title`, and `description`
(`opencontractserver/utils/metadata_file_parser.py:45-52,151-250`) and the ZIP
task only applies title and description
(`opencontractserver/tasks/import_tasks.py:1080-1091`). Adding durable
per-document metadata requires an explicit import-contract change.

### 6. Existing tests miss the integration boundary

`test_customs_ruling_citation_service.py` is a pure regex/helper test module.
It verifies pattern extraction and title extension stripping, but creates no
text document, annotations, references, or corpus graph. It cannot detect the
format gate or metadata/path identity mismatch.

The generic writer already has span fallback coverage
(`opencontractserver/tests/test_enrichment_writer.py:704-725`), but customs
enrichment has no database-backed tests proving that it invokes that behavior.

## Non-root causes and important constraints

- The first deterministic 10K slice contains HQ numeric legacy rulings. The
  citation regex intentionally only recognizes prefixed identifiers such as
  `H022844` and does not mine bare six-digit legacy values because they collide
  with money, statutes, and ZIP codes. This reduces observed citation yield in
  that slice, but it does not explain the zero result: HTS extraction should
  still have produced output, and all documents were skipped before matching.
- The source database contains 13,624 HTS entries and 301 extracted ruling
  citation candidates in this 10K slice, but none of those 301 citation targets
  is also in the slice. After the format fix, this particular ordered benchmark
  should yield HTS spans and may yield unresolved citation mentions, but it
  should not be used to assert nonzero resolved internal references or graph
  edges. Use a citation-closed or deliberately mixed fixture for that assertion.
- Do not broaden the bare-number regex as part of the span fix. Treat any
  context-aware legacy-number detector as separately measured product work with
  a false-positive corpus and explicit acceptance thresholds.
- DOC/PDF success does not validate this path. It validates the existing
  `TOKEN_LABEL` branch only.
- An arbitrary document rename can change a `DocumentPath` basename. For the
  current official CROSS layout, path-derived identity is a correct minimal
  fix. Long-term source identity should be stored in a dedicated durable field
  (for example, a namespaced `DocumentPath.external_id`) once the ZIP metadata
  contract supports it.

## Recommended implementation

### A. Make anchoring type an input to persistence, not an eligibility gate

1. In `CustomsRulingCitationService.enrich_corpus()`, accept both
   `TOKEN_LABEL` and `SPAN_LABEL` results from
   `load_document_text_and_layer()`. Only skip an exception, missing text, an
   unsupported annotation type, or a TOKEN result missing its required layer.
2. Rename `documents_skipped_not_pdf`. It currently counts loader errors and
   supported non-PDF input. Use a truthful metric such as
   `documents_skipped_unanchorable`, with optional breakdowns for load failure
   and unsupported type.
3. Pass `ann_type` into `_write_hts_annotations()` and remove the unused
   `layer` argument from `_build_citation_resolutions()`.
4. Pass the active `Analysis` into HTS creation and save it on newly created
   rows. Citation mentions already receive `analysis` through
   `EnrichmentWriter`; current HTS rows do not, leaving run provenance split.

### B. Write HTS results as spans for text documents

Keep the current PDF branch unchanged. For a `SPAN_LABEL` source document, use
the same no-page convention as the existing text anchorer:

```python
Annotation.objects.create(
    raw_text=raw_text,
    page=0,
    json={"start": start, "end": end, "text": raw_text},
    annotation_label=span_label,
    annotation_type=SPAN_LABEL,
    structural=False,
    data={"code": code, "char_span": {"start": start, "end": end}},
    # document/corpus/creator fields as in the existing branch
)
```

Use an `HTS_CODE` label whose label type matches the annotation type. Retain
`data.char_span` for a uniform dedupe/reconciliation key, but inspect all
existing `HTS_CODE` labels and dedupe against both representations so a legacy
span and a later token representation at the same character offset do not
duplicate:

```python
Q(json__start=start) | Q(data__char_span__start=start)
```

This mirrors the generic writer's existing dual-representation logic. Apply the
sidecar reconciliation policy above rather than silently leaving incompatible
label rows in a new implementation. Do not put fake page/bounding-box data on a
text annotation.

### C. Reuse `EnrichmentWriter` for citations, with the text-span sentinel fix

Build resolutions from the text offsets for both anchor types, then call
`writer.write(...)` as today. For TXT, `_layer_for()` checks the document type
and returns `None`, so the writer creates a span mention. It will still create
the associated `CorpusReference` and resolve/reconcile the document graph.

Change the writer's span fallback from `page=1` to `page=0` and include the
anchored text in its JSON payload. Keep its existing `OC_REF_DOC` label and
dual-representation dedupe behavior. Treat any existing producer
`CITED_RULING` annotation according to the explicit policy in root cause 4.

Avoid duplicating the writer's link, provisional-reference, graph, and
idempotency behavior in the customs service.

### D. Resolve CROSS citations using source identity, not title

For the immediate fix, build a corpus-wide mapping of current active
`DocumentPath.path` to document, then derive the CROSS identity from the path
basename:

```python
def _ruling_number_from_path(path: str) -> str:
    return Path(path).stem.upper()
```

Use this for both the source document's own number and the target lookup. Scope
the path query to the same visible document set used by enrichment, preserve
the existing deterministic order, and define a safe policy for duplicate source
identities (log and leave ambiguous target citations unresolved rather than
silently choosing one).

For the durable contract, extend the ZIP metadata parser and import task to
carry a structured ruling number into `DocumentPath.external_id` (or an agreed
namespaced equivalent). The field already exists on `DocumentPath`; merely
adding a CSV column will not populate it. Use priority order:

1. `DocumentPath.external_id` with an agreed `cross:` namespace
2. current corpus path basename for legacy official exports
3. title stem only as backward-compatible fallback

Keep the subject as the display title. Do not replace the title with an ID just
to make resolution work.

### E. Bound and measure TXT loading

The zero-output run nevertheless fetched every text layer. The service has
`PREFETCH_WORKERS = 12` while the observed S3 connection pool has 10 slots,
which logged connection-pool-full warnings. Make prefetch concurrency an
explicit setting, cap it to the storage-pool capacity, and record load latency,
load failures, matching time, and write time separately. This is a P2
performance follow-up, not a reason to delay correctness.

## Required tests

### Unit and service tests

1. `load_document_text_and_layer()` returns text plus `None` plus `SPAN_LABEL`
   for a `text/plain` document with `txt_extract_file`.
2. A two-document text corpus with paths `/HQ/H100001.txt` and
   `/HQ/H100002.txt` runs customs enrichment and creates:
   - an `HTS_CODE` `SPAN_LABEL` annotation with exact `json.start/end/text`,
     `page=0`, raw text, code, and matching span label;
   - an `OC_REF_DOC` `SPAN_LABEL` mention for an `H100002` citation with
     `page=0`;
   - a resolved `CorpusReference` and one `DocumentRelationship` edge.
3. A citation to an absent prefixed ruling creates an unresolved
   `CorpusReference` and no graph edge.
4. A title containing a subject instead of a ruling number still resolves via
   the current corpus path. Include title collisions and a control character to
   prove title is not part of identity.
5. Re-run the service and assert no duplicate HTS annotations, mentions,
   references, or graph edges.
6. Preserve the current PDF test fixture and assert it still produces
   `TOKEN_LABEL` annotations with valid PAWLS payload/page data. The fix must
   add a branch, not downgrade PDFs to spans.
7. Loader error and unsupported type cases increment the renamed skip metric
   accurately and do not mark a text document as "not PDF."
8. Seed a legacy importer-style `SPAN_LABEL` annotation attached to a
   `TOKEN_LABEL` `HTS_CODE` label and a `CITED_RULING` source span. Assert the
   selected reconciliation policy: no duplicated HTS highlight, correct
   `OC_REF_DOC` reference mention, and no invariant violation.
9. Assert HTS rows record the service `Analysis`, and canonical-key collisions
   are reported/unresolved rather than silently overwritten.

### Contract/integration test

Add a small real-CROSS fixture (roughly 20 rows, intentionally including a
prefixed citation, an HTS code, an unresolved citation, and subject titles) and
exercise this path:

1. Generate the official bulk ZIP.
2. Import it through `zip-to-corpus`.
3. Wait for all documents to settle; never treat HTTP 202 as import completion.
4. Run `enrich_customs_rulings`.
5. Assert nonzero HTS output, at least one span citation mention, one resolved
   reference/edge, one unresolved reference, and stable counts on a rerun.

This is the regression test that would have prevented the current release
blocker.

## Definition of done

- The official TXT export produces span annotations and references without PDF
  conversion.
- PDF/TOKEN output remains token-anchored and passes existing behavior tests.
- Canonical ruling-number resolution is independent of display title.
- A rerun is idempotent across both anchor representations.
- Text annotations use `page=0` and a consistent span JSON shape; they never
  advertise a nonexistent PDF page.
- Existing importer-style sidecar spans have an explicit tested reconciliation
  or migration policy rather than silently producing duplicate highlights.
- HTS and citation rows have consistent analysis provenance, and ambiguous
  canonical IDs are observable rather than resolved arbitrarily.
- The command summary distinguishes supported TXT processing from genuine load
  or anchoring failures.
- The real-export integration test passes and reports nonzero expected output.
- A 10K rerun is profiled with bounded storage concurrency; warnings from
  exceeding the configured S3 pool are eliminated or explicitly justified.

## Suggested sequencing

1. Write the two-document TXT service regression test first; reproduce the
   current all-skip failure.
2. Implement A through C and make the test pass.
3. Implement path-derived identity and its subject-title regression test.
4. Add the small official-export integration fixture.
5. Run a representative mixed HQ/NY corpus sample before judging citation
   recall. Track prefixed and intentionally excluded bare-number candidates
   separately.
6. Add durable per-document source metadata as a follow-up import/export
   contract change rather than hiding it inside the title field.
